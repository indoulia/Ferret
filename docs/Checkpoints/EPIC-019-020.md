## The three identity decisions, and why

- **A commit is its object id, unscoped.** A Git hash is a content hash of the
  commit object: the same commit in a fork and its upstream is the same commit.
  Scoping it to a repository would make "which release contains this fix"
  unanswerable across a fork. Proven with a real clone whose origin was
  rewritten, so the two repositories differ and the commit ids do not.
- **A developer is a lowercased email address — for now.** One person commits as
  several; EPIC-036 resolves them, and EPIC-006 models `emails` as a list so it
  has somewhere to put the answer. Merging two addresses here would make
  EPIC-036's decision by accident. No address means no developer, because
  inventing one from a display name merges every anonymous author into one
  person.
- **A file is its repository and its path.** A rename therefore produces a
  different entity, linked by the rename relationship — which is what Git
  recorded, a similarity score rather than an identity claim. **EPIC-023 must
  agree with this scheme**, or a file found by walking and the same file found in
  history become two entities.

## Notes for whoever picks this up

- **Never raise the runner's 16 MiB output cap.** Hitting it means page.
- **A merge has no changes, and that is correct.** Git prints none because the
  answer depends which parent you compare against.
- **Use `since`, not `skip`, for a running index.** Offset paging walks the
  history to reach the offset.
- **`parseLog` is exported for a reason.** Change it and the unit fixtures will
  tell you immediately; change it and only run the integration suite and you
  will wait ninety seconds to find out.
- **A commit's valid time is the commit time,** not the observation time. Git
  knows it. This is the difference from EPIC-018, where a branch's containment has
  no knowable start.

## Known limitations

Full table in the validation evidence §7. Carried forward:

- Offset paging is O(offset) → **EPIC-032**
- A SHA-1 collision would merge two commits → **EPIC-082**
- Merge changes absent; choosing `-m` or `--first-parent` is a modelling
  decision → **EPIC-032**
- Two addresses are two developers → **EPIC-036**
- File entities carry only path and extension → **EPIC-022/023**
- **One unexplained intermittent failure** in a single full run, name not
  captured, not reproduced in four subsequent runs. Recorded rather than
  dismissed; CI runs the suite three more times per PR.

## Next step

**EPIC-022 — File Discovery** and **EPIC-023 — File Identity & Content Hashing**,
which are the last pieces before **EPIC-031 — Incremental Indexing** can store
any of this.

EPIC-023 is the one to think about first, because **its identity scheme must
match EPIC-020's**: a file discovered by walking a worktree and the same file
seen in a commit must be one entity. EPIC-020 chose repository + path. If
EPIC-023 chooses differently, every file in Ferret exists twice.

The other thing waiting at EPIC-031 is the relationship-identity problem
EPIC-018 recorded: re-emitting an unchanged structural edge at a later instant
produces a new id, so ingestion must treat an open interval with identical
endpoints as a no-op or storage grows without bound for content that never
changed.
