# EPIC-030 — File Structure & Metadata: validation evidence

**Status: VALIDATED** · no new dependency, no new I/O. Detection is EPIC-024's,
reused; the rest is one pass over text Ferret already decoded.

## What the Epic does

`describeFileStructure(path, bytes)` returns a `FileStructure`: line count, line
ending, trailing newline, longest line, encoding, binary verdict, media type,
and — the part that matters — a single `classification` with the reason that
decided it, plus independent `generated` and `vendored` flags.

`fileAttributesFrom` and `fileVersionAttributesFrom` turn that into canonical
attributes, and `emitFiles` records them when a caller supplies structure.

## Design decisions worth recording

**One classification, two flags.** A minified bundle inside `node_modules` is
genuinely generated *and* vendored. A single enum would force one to be a lie,
and a set would force every consumer to write precedence logic. So the
classification is single-valued and precedence-ordered for the consumer that
needs one answer, and the two booleans are independent for the consumer asking a
specific question.

**Vendored beats generated in the classification.** "This is a dependency" is
the more useful thing to know about a minified file in `node_modules`, and
nothing is lost either way because both flags are set.

**Markers are only read near the top of the file.** A generated marker is a
convention about where a file *starts*. Scanning the whole file would mark any
file that discusses the convention — including `structure.ts` itself — and, more
seriously, would let a repository change how a file ranks by burying a marker in
it. The window is 4 KiB and there is a test for a marker just past it.

**Every classification carries its reason.** `build directory dist/`,
`marker "@generated"`, `lockfile package-lock.json`. Governance §6 forbids a
derived judgement that cannot be explained, and "why is this marked generated"
is the first question anyone asks. The tests assert the exact reason strings
rather than just the verdict, so a reason cannot quietly become useless.

**`undefined`, not `0`, for a binary file's line count.** Zero is a claim that
the file has no lines; `undefined` says the question does not apply. The
attribute fragment omits the key entirely rather than writing a null.

**Directory matching is exact, on segments.** `distribution/` is not `dist/`,
and there is a test for it. Every pattern is a literal comparison rather than a
regular expression with a quantifier, because these run over
attacker-controlled paths.

**`extensionOf` moved into the core.** It lived in `git/files.ts` because
EPIC-022 needed it first. Two copies would eventually disagree about a dotfile
or a trailing dot, so the definition moved to `src/files/paths.ts` and the Git
provider re-exports it — providers may depend on the core, never the reverse.
The test asserts object identity.

**The canonical model spells the vocabularies out rather than importing them.**
`attributes.ts` depends on nothing but zod, and importing upward into
`src/files/` to reach two string unions would trade that for no benefit. The
duplication is guarded by a test that parses every `FILE_CLASSIFICATIONS` value
through the schema and rejects an invented one.

**`ENTITY_SCHEMA` stays at version 1.** The entity *envelope* is unchanged; only
a kind's attribute schema grew, which is exactly the extension EPIC-006 AC-4
anticipated.

## Limitations

- **Nothing here reads a file.** `emitFiles` takes structure from its caller,
  and no caller supplies it yet — wiring content into indexing belongs to the
  Epic that makes indexing read content. Until then these attributes are
  available and unused, which the `emits exactly as before` test pins down.
- **`.strict()` and additive attributes.** Adding optional fields is forward-
  compatible for writers and *not* for readers: an older build reading a newer
  entity would reject the unknown key rather than ignore it. That is a property
  of the existing model, surfaced by this Epic rather than introduced by it, and
  the version number does not currently express it.
- **Classification is heuristic and English-shaped.** The directory names, file
  names and markers are conventions, not standards. A project that puts
  generated output in `artifacts/` is classified `source`.
- **A marker is a claim by the repository.** It changes how a file ranks, never
  whether it is readable or whether a security control applies — but a
  repository can mark its own files generated, and this Epic accepts that.
- **`maxLineLength` counts characters, not columns or bytes.** A tab is one.
- **Language is not populated.** `fileAttributes.language` exists and remains
  empty: the media type is what detection establishes, and mapping it to a
  language name belongs with the parser that claims it.
- **No test/source pairing.** Knowing `a.test.ts` is a test does not link it to
  `a.ts`; that is a relationship, and EPIC-049 owns those.
