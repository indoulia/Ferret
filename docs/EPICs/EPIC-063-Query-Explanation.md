# EPIC-063 — Query Explanation

**Status: APPROVED | Priority: P1 | Domain: Context Compilation**

> Authored to the [Epic Specification Standard](EPIC-SPECIFICATION-STANDARD.md).
> Registered in the [Epic registry](README.md) under Context Compilation, where it
> has been named and prioritised since the registry was written; only the
> specification is new.

## 1. Objective

Say why a query returned these results in this order — in sentences, from
Ferret's own recorded fields, and never by guessing.

## 2. Value — the signals exist and nobody can read them

Three Epics built the material and each deferred the explaining:

- **EPIC-059's validation** — "No answer packs, and no explanation of why a
  result was chosen. A pack says *that* an item matched, not how the query was
  planned. — **EPIC-060**, **EPIC-063**". EPIC-060 shipped; this half did not.
- **EPIC-060 §4** — "A user-facing narrative explanation of the query — EPIC-063.
  This Epic returns `QueryPlan` as it stands; it does not compose prose about it."
- **EPIC-056 §4** — "Query explanation as a product surface — EPIC-063. The
  breakdown here is a field on a hit, not an explanation feature."

The result is a capability that exists and cannot be reached. `QueryPlan` records
the shape, the reason, and every strategy that ran or was skipped and why.
EPIC-056 and EPIC-057 put `relevance`, `contributors`, `subsumed`, `standing` and
`why` on each hit. `WithheldReport` counts what permission removed. And
`describeHit` in the MCP surface **emits none of it** — a client gets an opaque
`score` and no way to ask why one hit beat another.

Governance §18 requires Ferret to "explain why evidence was included, excluded,
considered authoritative, considered stale, or considered conflicting". Every one
of those five is recorded somewhere and none of them is said.

## 3. Scope

- A **`QueryExplanation`** composed from the plan, the ranked hits and the
  withheld report.
- **Comparative ranking notes**: for each adjacent pair in the result, the *first
  ordering key on which they differ* — which is what "why is this one above that
  one" actually asks.
- **Strategy narration**: which strategies ran, what each returned, and the
  recorded reason any was skipped.
- **Withholding narration**: how much was withheld and for which reason, without
  saying what.
- **An honest "cannot say"** for a hit that carries no breakdown.
- **A renderer**, matching `renderAnswer` and `renderPack`.
- **`ferret_explain`** on the MCP surface, and `ranking` added to `describeHit`
  so the structural signal is reachable as well as the prose.

## 4. Non-scope

- **Producing the signals.** Shape and strategies are EPIC-055's, relevance
  EPIC-056's, standing and authority EPIC-057's, withheld counts EPIC-058's,
  evidence reasons EPIC-062's. This Epic reads all of them and derives none.
- **Explaining a *subject*** — EPIC-048's `ferret_why`, which answers "why does
  Ferret believe this about that entity". This Epic answers "why did this query
  return this". Both are explanations; they explain different things and §8.5
  keeps them apart.
- **Model-written prose.** No sentence here is generated by a model, and §8.1
  makes that a contract rather than an implementation note.
- **Storing explanations.** Composed on demand. EPIC-060 §4 already recorded why
  a cache is not free: "writing rows nothing reads is the write-only-subsystem
  defect EPIC-048 was written to correct."
- **Changing any ranking.** An explanation that could alter what it explains is
  not an explanation.
- **Confidence — EPIC-046. Conflicts — EPIC-047.** Reported where recorded.
- **A new table, column or migration.**

## 5. Inputs

- `QueryPlan` — shape, reason, `exact`, `StrategyOutcome[]`, `partial`.
- The ranked hits, each with its `RankBreakdown` where one exists.
- `WithheldReport` — totals by reason.
- The question as asked.

## 6. Outputs

- `src/retrieval/explain.ts` — `explainQuery`, `renderExplanation`, core and pure.
- `ferret_explain` on the MCP server; `ranking` on every search hit it returns.
- No schema change.

## 7. Dependencies

EPIC-055 (the plan), EPIC-056 and EPIC-057 (the breakdown and the key order),
EPIC-058 (withheld counts), EPIC-064/065 (the MCP surface to register on).

## 8. Contracts

### 8.1 Every sentence comes from a recorded field

An explanation is composed by naming fields, kinds, counts and recorded reasons.
Nothing is inferred, nothing is generated, and **no sentence is composed about
source content**. A hit is described as "a `file`, matched in its body, standing
0" — never as "a file about authentication".

Two consequences, both deliberate:

- **It cannot leak.** An explanation contains no repository text, so it needs no
  EPIC-084 containment and cannot carry an injected instruction. `highlight` is
  the one field that *is* content and it is not part of an explanation; a client
  that wants it already has it on the hit.
- **It cannot flatter.** Where a signal is absent the explanation says so (§8.4).
  A plausible sentence with nothing behind it is worse than no sentence, which is
  the same rule EPIC-060 applied to claims.

### 8.2 "Why is this above that" is answered by the first key that differs

EPIC-057 §8.3 fixed the ordering:

```
standing asc → relevance desc → authority desc → recency desc
             → kind asc → sourceId asc → id asc
```

So for any adjacent pair the explanation walks those keys in order and names the
first one on which they differ, with both values. That is the whole mechanism,
and it is why this is checkable rather than rhetorical: the answer is a fact
about the comparator, not a judgement about the results.

A pair identical on every key including identity cannot occur — the tail makes
the order total — so "they tie" is reported only for the keys above identity, as
"separated only by identity, which is the determinism tail".

### 8.3 The plan is narrated including what did not happen

A strategy that did not run is the most useful line in an explanation and the one
a client never sees today. `StrategyOutcome.skipped` already carries the sentence
— "No embedding provider is registered. Ferret ships none by design" — and
`QueryPlan.partial` already says an answer may be incomplete. Both are surfaced
verbatim; neither is paraphrased, because the recorded wording is the wording
that was reviewed.

### 8.4 An explanation may say it cannot explain

A hit with no `RankBreakdown` — an exact-identifier answer, where EPIC-055
deliberately applies no ranking — is explained as exactly that: "answered
exactly; no ranking was applied". A hit from an unplanned path with no breakdown
at all is reported as "no ranking breakdown was recorded for this hit", never as
a reconstructed guess.

### 8.5 `ferret_explain` explains a query; `ferret_why` explains a subject

The two are separate tools with separate questions, and neither is a superset.
`ferret_why` answers "how does Ferret know this about that entity" from evidence.
`ferret_explain` answers "why did this question return these results in this
order" from the plan and the ranking. A client asking the second and getting the
first would be told about provenance when it asked about retrieval.

`ferret_explain` re-runs the query it is explaining, under the caller's own
authorization. It cannot explain a result set it was handed, because a handed
result set is unverifiable input and explaining it would mean describing rows
this caller may not be allowed to see.

## 9. Acceptance criteria

- **AC-1** An explanation names the question, the shape it was read as, and the
  recorded reason for that reading.
- **AC-2** Every strategy in the plan appears, with what it returned.
- **AC-3** A skipped strategy's recorded reason appears verbatim.
- **AC-4** `partial` is stated when any strategy was skipped or failed.
- **AC-5** For each adjacent pair of hits, the explanation names the first
  ordering key on which they differ, with both values.
- **AC-6** A pair differing only below recency is reported as separated by the
  determinism tail, not by a judgement.
- **AC-7** A hit whose relevance came from more than one contributor says which.
- **AC-8** A hit that folded a constituent says how many and which kind.
- **AC-9** A hit with standing above live carries its recorded `why` verbatim.
- **AC-10** A hit with no breakdown is reported as unexplained, not reconstructed.
- **AC-11** An exact answer is explained as exact, with no ranking claimed.
- **AC-12** Withheld counts appear by reason; no withheld value appears.
- **AC-13** No explanation contains any entity attribute value, statement or
  highlight — asserted over a real query, not only by inspection.
- **AC-14** `explainQuery` is pure: same inputs, same output, no query.
- **AC-15** `ferret_explain` is registered, read-only, and refuses without READ.
- **AC-16** `describeHit` emits `ranking`, so the structural signal is reachable.
- **AC-17** The renderer's output is stable for stable input.

## 10. Test requirements

**Unit** — every AC over hand-built plans and hits: each ordering key as the
first difference, the determinism tail, multi-contributor and folded hits, the
standing sentence, the missing breakdown, the exact answer, withheld by reason,
purity, and renderer stability.

**Integration (real PostgreSQL)** — an explanation of a real query over an
indexed repository; AC-13 asserted by taking every attribute value, statement and
highlight in the result and checking none appears in the explanation.

**Security** — AC-13 and AC-15; and the structural check that `explain.ts` cannot
read anything, on the same footing as `rank.ts` and `freshness.ts`.

**Failure** — an empty result, a plan with no strategies, a hit with a malformed
breakdown, a question at the length bound.

## 11. Security requirements

An explanation is composed of Ferret's own structural fields and contains no
repository text (§8.1), which is why it needs no containment and cannot be an
injection vector. `ferret_explain` re-runs its query under the caller's
authorization (§8.5) and reports withheld counts only, never withheld values —
the disclosure EPIC-058 §16 already characterised as deliberate and bounded.

## 12. Observability

The explanation *is* the observability, which is the point: Governance §18 asks
for an explanation a caller receives, and every signal it reads was previously
recorded and unreachable.

## 13. Performance constraints

`explainQuery` is one pass over the hits and one over the adjacent pairs, both
bounded by the caller's limit. `ferret_explain` costs exactly one search.

## 14. Definition of Done

Scope implemented; AC-1 to AC-17 satisfied with evidence in
`validation/EPIC-063-VALIDATION.md`; unit, integration, security and failure
tests present and passing; `npm run verify` green; registry updated; EPIC-059's
recorded gap struck with a dated note rather than edited away.

## 15. Governance alignment

- **§18 Provenance and Explainability** — the five things Ferret "should be able
  to explain" are recorded in five different places; this is where they are said.
- **§6 Evidence Before Inference** — §8.1 and §8.4. An explanation that guessed
  would be inference presented as provenance, which is the worst version of this
  feature.
- **§3 AI-Operated by Default** — the surface is an MCP tool, because that is the
  interface the product is built for.
- **§2 Simplicity** — one pure function and a renderer. No storage, no model, no
  new column.

## 16. Raised, not absorbed

- **`ferret_search` does not return an explanation inline.** It returns `plan`
  and now `ranking`, and a caller wanting prose calls `ferret_explain`. Bundling
  a paragraph into every search response would spend a client's context on an
  explanation it did not ask for, which is the concern EPIC-061 exists for.
- **The five Governance §18 verbs are not all equally served.** "Included",
  "excluded", "considered authoritative" and "considered stale" are all recorded
  and said. "Considered conflicting" is EPIC-047, which is unbuilt: this Epic
  reports a conflict where EPIC-062 recorded one and invents nothing where it did
  not.
- **An explanation cannot say why something was *not* found.** Nothing records
  the absence, so an honest explanation cannot describe it. That would need a
  "why did this miss" capability with no owner in the registry today.

## 17. Recorded during implementation

- **`ferret_explain` carries no content notice**, unlike every other tool. §8.1
  is why it is safe, and AC-13 is what holds it honest; the integration test
  asserts the absence and the claim together.
- **Folded parts are reported as a count, not as kinds.** `subsumed` records ids,
  so naming kinds would need a second lookup and reporting one the breakdown does
  not carry would be this Epic inventing a detail — §8.1 applied to its own
  output.
