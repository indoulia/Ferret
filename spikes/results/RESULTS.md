## Benchmark fairness corrections

Three benchmarks were rewritten after the first two runs exposed that they were
measuring my implementation choices rather than the runtimes:

- `fsscan`: the Node version used a sequential `await readFile` loop (963 ms). Bounded
  parallelism cut it to 363 ms. Both runtimes now measure **both** a sequential and a
  concurrent strategy and are credited with their best.
- `git`: the Python version ran its three git calls serially while Node ran them via
  `Promise.all`. With the calls parallelised, Python went 435 ms -> 155 ms, turning a
  2.4x Node win into a tie.
- `concurrency`: Python used only a process pool, which is expensive on Windows. Adding
  a thread pool (hashlib and file I/O release the GIL) took Python from 512 ms to 231 ms,
  turning a 2x Node win into a Python win.

Two of the three corrections moved the result **against** the eventual recommendation.

## Cross-platform (Linux, containers)

Node `node:22-slim`, Python `python:3.12-slim`. macOS was **not** measured - no macOS host was available.

| Benchmark | Node (Linux) | Python (Linux) | Faster |
|---|---:|---:|---|

| `concurrency` | 491.7 ms | 48.3 ms | **Python** 10.18x |
| `treesitter` | 2.05 s | 1.33 s | **Python** 1.54x |
| `parse_csv` | 890.5 ms | 259.3 ms | **Python** 3.43x |
| `parse_xlsx` | 714.7 ms | 2.06 s | **Node** 2.88x |
| `parse_docx` | 356.9 ms | 261.2 ms | **Python** 1.37x |
| `parse_pdf` | 406.6 ms | 1.05 s | **Node** 2.58x |

- Both stacks install and run on Linux with no native toolchain and no source builds.
- Python's filesystem scan is 5x faster than Node's on Linux (94.6 vs 483.1 ms) but 1.6x SLOWER on Windows (596 vs 363 ms). The ranking reverses by platform.
- Python's process-pool concurrency is 10x faster than Node's worker_threads on Linux (48.3 vs 491.7 ms), but on Windows process spawn is expensive and Python's thread pool (231 ms) is its best model against Node's 316 ms.
- Parser rankings are stable across platforms: Node faster on PDF and XLSX, Python faster on CSV, DOCX and tree-sitter.
- Robustness outcomes are identical across platforms for both stacks - no platform-specific parser failure appeared.

## Robustness on malformed and adversarial input

16 cases per runtime, each parsed in an isolated process with a 30 s timeout: truncated (50% and 5%), bit-corrupted, empty, wrong-magic, a decompression-amplification OOXML (40 MB expanding from a tiny archive), and an OOXML carrying an external-entity (XXE) declaration.

| Outcome | Node | Python |
|---|---:|---:|
| clean_error | 13 | 12 |
| ok | 3 | 4 |

- **No crashes, no hangs, no timeouts in either stack.** Every parser in both stacks either rejected hostile input or returned without stalling.
- **Neither stack resolved the XXE external entity.** Verified directly: the target file's contents did not appear in the extracted text.
- **Behavioural difference that matters for Ferret:** on the XXE document `mammoth` (Node) raised an error, while `python-docx` returned **empty text with no error**. Silent emptiness would let Ferret record "this document has no content" as evidence. Under Governance 6 (Evidence Before Inference) a loud rejection is the safer failure mode.
- Both CSV readers accept corrupt CSV without complaint - inherent to CSV, not a defect, but it means CSV ingestion needs Ferret-side validation rather than parser-side trust.

## Dependency, licence and maintenance assessment

| | Node | Python |
|---|---:|---:|
| Packages installed | 228 | 42 |
| Vulnerabilities before remediation | 1 high, 2 moderate | 25 advisories across pypdf and mcp |
| Vulnerabilities after remediation | 0 high, 2 moderate | 0 (pip-audit clean) |
| Deprecated transitive packages | 6 | 0 |
| Native builds required | 0 | 0 |
| Copyleft on a mandatory path | no | **yes** - psycopg is LGPL-3.0-only |
| Undeclared licence in tree | **yes** - `buffers@0.1.1` | no |

- Node pulls 228 packages to Python's 42 for the same capability set - a 5.4x larger transitive attack and maintenance surface.
- Every deprecated package and both remaining moderate CVEs in the Node stack trace to a single dependency, exceljs, which is also the stalest direct dependency in either stack (last published 2024-12-20).
- Python's only licence problem, psycopg's LGPL-3.0, sits on the mandatory database path and cannot be avoided by swapping a parser; Node's licence problem (unlicensed `buffers`) is confined to exceljs and disappears if the XLSX library is replaced.
- Both stacks reached a zero-high-severity state after remediation.
- tree-sitter grammar versions differ between the two ecosystems (Node counted 758,096 named nodes vs Python 749,220 over the identical 1,590 files, ~1.2% apart). Ferret must pin grammar versions explicitly, since AST shape is part of its canonical model.
